# GPT 문항 대응 재설계안

작성: 2026-09-14. 상태: 별도 워크트리에서 구현 및 검증. 조사 기준: `780b288`.

## 1. 해결할 문제와 목표

현재 비교기는 질문을 문자열로 정리한 뒤 전체 일치, 긴 지침 비교, 표시된 안내 분리, 문자 유사도 순으로 대응을 찾는다. 분량과 번호를 해석하는 책임이 여러 함수에 나뉘어 있어 새로운 표시 조합이 나오면 추가 규칙이 필요하다. 사용자가 선택한 문항 대응도 다음 응답에서 재사용하지 않는다.

목표는 **표시 형식이 바뀌어도 같은 문항이라는 근거를 유지하고, 근거가 부족할 때는 그 이유와 선택할 대상만 보여주는 것**이다. 질문의 대응과 답변의 요구 충족 여부는 구분한다. 질문의 분량 안내가 생략되어도 같은 입력칸일 수 있지만, 대응 성공이 답변 분량이나 내용의 적합성을 보증하지는 않는다.

임의의 한국어 재서술, 번호가 없는 답변 본문만 있는 경우, 서로 구별할 정보가 없는 문항까지 자동 판별한다고 보장할 수는 없다. 특히 현재 확장에는 의미를 추론하는 언어 모델이 없다. 개발에 사용하는 모델의 추론 수준을 높여도 확장 실행 시 그 능력이 생기지는 않는다.

기존 원칙을 유지한다: 회사별 분기 없음, 별도 서버/API 없음, GPT에 ID나 새로운 출력 규약 요구 없음, 사용자 선택 응답에만 적용, 답변 원문 보존, 저장 버튼 미호출.

## 2. 현재 코드에서 확인한 경계

가상 질문 `지원 직무에 관심을 갖게 된 이유와 앞으로의 목표를 기술하십시오.`를 사용해 현재 `JSLGpt.map`에 직접 입력했다. 아래는 개별 경계 탐색 결과이며 전체 성능이나 실제 사이트 검증 결과가 아니다.

| 변경한 조건 | 현재 자동 대응 | 현재 추천 |
|---|---|---|
| 질문 뒤 `(700자 이내 (영문작성 시 1400자))` | 가능 | 해당 없음 |
| 질문 앞 `[700자 이내]` | 불가 | 있음 |
| 질문 다음 줄 `700자 이내 / 영문 1400자` | 불가 | 없음 |
| 질문 앞 `①` | 불가 | 있음 |
| 질문 앞 `(※구체적인 사례를 사용해도 됩니다)` | 불가 | 없음 |
| 동기와 목표를 묻는 문장을 다른 표현으로 재서술 | 불가 | 없음 |
| `관심을 갖게 된 이유`를 `관심을 갖지 않는 이유`로 변경 | 불가 | 있음 |
| 질문은 같고 응답 번호만 1에서 2로 변경 | 불가 | 있음 |

추천은 자동 입력되지 않는다. 다만 번호 충돌과 일부 부정 표현도 추천될 수 있으므로, 자동 대응뿐 아니라 추천에도 충돌 검사가 필요하다.

확인 위치: [비교기](../src/core/gpt-protocol.js), [응답 추출/UI](../src/features/gpt-response.js), [연결·적용 준비](../src/core/gpt-background.js). 현재 동작 계약은 [SPEC](../SPEC.md)과 [검증 문서](../tests/gpt/README.md)를 따른다.

## 3. 처리 구조

`완료된 응답 추출 → 질문 구조화 → 모든 대상과 근거 비교 → 중복·충돌 검증 → 자동 대응 또는 사용자 선택 → 기존 입력 검증`

### A. 질문과 답변의 출처를 보존한다

코드 블록이 어느 질문 설명에 속하는지와 그 질문이 어느 입력칸인지 따로 판정한다. 잘못 추출된 질문에 비교만 정교하게 적용해도 결과는 틀릴 수 있다.

- 제목, 목록, 질문 원문, 코드 블록의 경계와 위치를 보존한다. 인접한 표·검수·다른 문항으로 질문 맥락을 넘기지 않는다.
- 문항 번호, 복합 문항명 `1-2`, 응답 내 목록 순번을 구별한다. `①`도 문항 제목 위치에서만 번호 후보가 되며 본문에 나온 숫자로 문항을 결정하지 않는다.
- 같은 문항의 초안·수정안 두 블록은 별도 후보로 보존한다. 마지막 블록을 임의로 선택하지 않는다.
- 답변을 못 찾음, 질문 출처가 모호함, 질문 대응 실패를 서로 다른 상태로 반환한다.
- 답변 내용의 소재나 회사명은 문항을 확정하는 근거로 사용하지 않는다.

### B. 양쪽 질문을 같은 구조로 읽는다

자소설의 원문과 GPT가 적은 질문에 같은 분석기를 사용한다. 질문을 삭제해 짧은 문자열만 남기는 대신, 각 구간의 원문·위치·분류 근거를 유지한다.

| 구간 | 처리 |
|---|---|
| 입력칸 ID, 순번, 명시적 문항명 | 각각 별도 필드로 보관. 실제 대상은 자소설 ID로 지정 |
| 질문의 요구 문장 | 기본 비교 대상. 알려진 표시 차이만 정리 |
| 분량·언어·공백 계산 안내 | 수치, 단위, 조건을 구조화. 질문 앞·뒤·별도 줄에서도 독립 구간이면 인식 |
| 선택적 예시 | 선택 사항이라는 근거가 있을 때만 생략 가능한 구간으로 분류 |
| 필수 조건·대상·기간·부정 표현 | 질문을 구별하는 정보로 보존 |
| 분류하지 못한 구간 | 원문 그대로 남기고 비교 근거가 부족함을 표시 |

괄호·줄바꿈·글머리표는 구간 경계를 찾는 단서다. `※`나 괄호가 있다는 이유만으로 작성 조건을 선택 사항으로 처리하지 않는다. `700자`와 `최근 3년`, `사례 2가지`도 구분한다. 한 구간에 분량과 필수 조건이 섞여 있으면 알려진 분량만 분리하고 나머지를 보존한다. 내부 경계를 확정하지 못하면 구간 전체를 보존한다.

표시 변환도 문맥을 제한한다. 번호 영역의 전각·원형 숫자, 공백과 종결 표현의 알려진 차이는 정리할 수 있지만, 질문 전체의 기호·공백을 무조건 삭제하지 않는다. 새로운 표현을 이해하지 못했을 때 임의로 핵심 문장이라고 분류하지 않는다.

### C. 점수와 확정 근거를 분리한다

각 응답과 각 대상 문항의 쌍에 다음 정보를 만든다.

```text
대응 근거: 원문 일치 / 표시 차이만 존재 / 명시적 번호·문항명 / 사용자가 확인한 대응
충돌: 번호 / 복합 문항명 / 요구 내용 / 대상·기간·개수 / 중복
불확실성: 해석하지 못한 문구 / 생략된 구별 정보 / 질문 출처
추천 점수: 사용자가 살펴볼 후보의 순위
```

자동 대응은 허용된 근거 조합과 대상 유일성으로 결정한다. 여러 약한 유사도 점수를 합쳐 자동 대응 기준을 넘기지 않는다. 충돌 검사는 원문과 구조화 결과를 함께 사용하며, 추천 순위를 계산하기 전에 수행한다. 한국어 부정과 의미 차이를 모두 검출할 수 있다는 가정을 두지 않는다. 검출하지 못한 의미 차이에 대비해 유사도만 있는 대응은 계속 사용자 선택 대상으로 둔다.

| 근거 | 결정 |
|---|---|
| 원문 또는 표시 차이만 정리한 질문이 유일하게 일치하고 명시적 식별자 충돌 없음 | 자동 대응 |
| 번호·문항명이 명확하고 요구 문장이 같으며 차이는 확인된 분량·선택적 예시뿐 | 중복·경쟁 대상이 없으면 자동 대응 |
| 명확한 `문항 2 수정안`처럼 질문 없이 식별자만 있는 기존 지원 형태 | 해당 식별자가 유일하고 충돌이 없으면 기존 자동 대응 유지 |
| 사용자가 확인한 동일 질문 표현이 다시 나타나고 저장 범위·현재 대상이 유효 | 현재 충돌·중복 재검사 후 재사용 |
| 재서술·요약으로 문자 근거가 부족함 | 충돌 없는 후보를 추천하고 사용자 선택 |
| 번호는 2번, 본문은 3번을 가리킴 | 양쪽 근거를 보여주고 사용자 선택 |
| 같은 질문이 여러 입력칸에 있거나 같은 문항에 여러 답변이 대응 | 사용할 대상·답변 선택 |
| 구별에 필요한 조건이 빠졌거나 분석하지 못한 문구가 남음 | 다른 충분한 근거가 없으면 사용자 선택 |
| 문항 정보 없이 답변 본문만 존재 | 출처를 확정하지 못한 상태로 유지 |

필수 조건이 생략된 것과 그 조건을 반대로 적은 것은 다르다. 생략 자체를 내용 충돌이라고 단정하지 않되, 생략된 정보로 서로 다른 문항을 구별하지도 않는다.

### D. 응답 전체의 대응을 검증한다

모든 후보와 모든 대상의 대응표를 먼저 만든다. 이후 자동 대응 가능한 관계만 검증한다.

- 한 입력칸에 두 답변이 대응하면 해당 충돌을 해결해야 한다.
- 순서가 바뀌거나 일부 문항만 있어도 각 후보의 판정 근거는 유지되어야 한다.
- 앞에서 선택된 문항을 빼고 남았다는 이유로 마지막 문항을 자동 확정하지 않는다.
- 응답 수와 문항 수가 같다는 이유로 일대일 연결을 강제하지 않는다.
- 구별되지 않는 질문을 추가하면 기존 자동 대응을 재검토한다. 관계없는 문항을 추가하거나 순서만 바꿔서는 대상이 달라지면 안 된다.
- 전체 점수 합계가 큰 배치가 개별 문항의 근거 부족이나 충돌을 덮지 못하게 한다.

## 4. 한 번 선택한 대응을 다시 묻지 않는 방법

현재 `choices`는 한 번의 적용 요청에서만 쓰인다. 새 구조에서는 **사용자가 명시적으로 선택하고 적용 결과까지 확인된 대응**을 로컬에 기억한다. 자동 대응 결과나 추천 표시 자체를 학습 근거로 저장하지 않는다.

저장 범위는 `ChatGPT 대화 ID + 지원서 ID + 연결 revision + 문항 구성 지문 + 분석기 버전`이다. 값은 `확인한 질문 표현의 지문 + 명시적 문항명/번호 + 대상 문항 ID`로 제한한다. 문항 구성 지문은 ID·번호·질문 원문으로 계산하며 답변은 포함하지 않는다.

- 같은 질문 표현과 검증된 표시 변형에만 재사용한다. 비슷한 새 문장을 확인된 표현으로 취급하지 않는다.
- 새로운 번호·본문 충돌이나 중복 후보가 있으면 저장된 대응도 자동 사용하지 않는다.
- 같은 표현을 서로 다른 대상에 선택한 이력은 모호한 대응으로 남긴다. 마지막 선택으로 덮어 학습하지 않는다.
- 질문이 없는 `수정안` 같은 일반 표현이나 출력 순번만으로는 재사용 규칙을 만들지 않는다.
- 연결 해제·변경, 문항 구성 변경, 분석기 버전 변경 시 기존 범위는 폐기한다. 잘못 기억한 대응을 삭제할 수 있게 한다.
- 다른 회사·다른 지원서·다른 대화로 전파하지 않는다. 따라서 새로운 지원서의 처음 보는 재서술까지 해결하는 장치는 아니다.
- 답변 본문을 추가로 장기 저장하지 않는다. 지문도 로컬 데이터이므로 보관 범위·삭제 방식·상한을 구현 때 [PRIVACY](../PRIVACY.md)에 반영한다.

적용 성공은 사용자가 선택한 대응을 기억할 수 있는 완료 시점이며, 알고리즘이 의미를 맞게 이해했다는 평가 정답은 아니다.

현재 문항에서 GPT로 보낸 질문의 출처를 이용하는 방법은 후속 확장으로 검토한다. 전송한 문항 ID를 로컬에 보존하더라도 실제 사용자 메시지와 선택한 응답의 관계를 확인해야 한다. 단순히 직전에 2번 질문을 보냈다는 이유로 이후 모든 코드 블록을 2번에 연결하지 않는다. 이 기능은 현재의 ‘선택한 assistant 응답만 읽기’ 계약을 확장하므로 첫 비교기 교체 범위에서 분리한다.

## 5. 사용자가 보게 될 결과

대응이 명확하면 기존 적용 흐름을 유지한다. 모호한 경우에는 이미 대응된 문항을 요약하고, 선택이 필요한 항목의 원문·차이·이유를 보여준다.

예: `4개 중 3개 대응 · 1개 선택 필요`, `번호는 2번, 질문은 3번과 일치`, `같은 본 질문이 두 문항에 있습니다`, `이 질문 표현에 대해 이전에 선택한 3번 문항`.

추천 문항은 선택값을 미리 채우지 않는다. 사용자는 해당 항목만 선택하거나 제외한 뒤 적용한다. 모호한 항목이 남은 상태에서 나머지를 몰래 먼저 쓰지 않는다. 기존 문항 이동·되돌리기·입력 직전 원문 검증은 유지한다.

## 6. 새 회사가 나올 때마다 코드를 고치는 일을 줄이는 검증

회사를 기준으로 테스트를 나누지 않고 **변화의 종류**를 기준으로 가상 질문을 생성한다. 같은 질문에 여러 변화를 조합한 경우까지 확인한다.

| 묶음 | 대표 변화 | 기대 |
|---|---|---|
| 표시 | 번호 표기, 괄호 종류·중첩, 안내 위치, 줄바꿈, 글머리표 | 허용된 표시 변형은 동일한 문항 ID |
| 질문 구별 | 성공/실패, 부정, 포함/제외, 필수 조건, 대상·기간·개수 변경 | 변경을 지워서 자동 대응하지 않음 |
| 구조 | 일부 응답, 역순, 복합 문항, 표·전략문 삽입, 같은 문항의 복수 답변 | 출처와 중복 처리 유지 |
| 대상 구성 | 같은 질문 추가, 무관한 문항 추가, 순서 변경 | 모호함 재검사, 순서·잔여 후보로 추론하지 않음 |
| 재사용 | 동일 표현 재등장, 충돌 있는 새 표현, 연결·질문 변경, 이력 삭제 | 허용 범위에서만 기억한 대응 사용 |
| 입력 흐름 | 분석 후 응답·답변 변경, 다른 탭, SPA 이동, 중복 클릭 | 기존 준비 토큰·검증·잠금 유지 |

표시 변형 테스트에서는 한 문장에 같은 변환을 반복하거나 조합해도 결과가 유지되는지 검사한다. 의미 변경 테스트에서는 표시 정규화가 그 차이를 지워 버리지 않는지 검사한다. 규칙 작성에 쓴 질문과 문장 구조가 다른 검증용 질문도 따로 둔다.

결과는 `틀린 자동 대응`, `맞는 자동 대응`, `추천 적합성`, `사용자 선택으로 남은 사례`를 유형별로 보고한다. 자동 대응률만 높이는 것을 성공으로 보지 않는다. 유한한 테스트에서 오대응이 0건이어도 모든 자연어에서 0건이라고 표현하지 않는다.

## 7. 구현 단위와 도입 순서

1. 질문 분석과 대응 근거 반환을 순수 모듈로 분리하고, 기존 회귀 사례와 위 경계 사례를 공통 데이터로 만든다. 원문·출처·분류 못한 구간을 반환하는 계약부터 고정한다.
2. 가상 데이터에서 기존/새 비교기의 판단을 함께 기록한다. 자동 대응이 달라진 사례는 이유를 검사한다. 테스트 중 비교만 수행하는 단계에서는 입력 기능을 추가하지 않는다.
3. 새 판정기를 기존 `map`의 `rows / qnas / packet` 계약 뒤에 연결한다. UI에는 실패 이유와 질문 차이를 전달한다. 확정되지 않은 대상은 패킷에 들어갈 수 없게 한다.
4. 사용자 선택 대응의 보관·삭제를 별도 변경으로 구현한다. 저장 정책과 안내를 함께 갱신한다.
5. 기존 [자동·브라우저 검증](../tests/gpt/README.md)을 실행하고, 가상 MV3 페이지에서 적용·선택·되돌리기·문항 이동·저장 미호출을 확인한다. 실사이트 확인과 구분해 결과를 보고한다.

예상 수정 위치는 `src/core/gpt-protocol.js`와 새 순수 분석 모듈, `src/features/gpt-response.js`, `src/core/gpt-background.js`, 관련 테스트·문서다. 모듈을 추가하면 [manifest](../manifest.json)과 service worker 로딩 순서를 함께 확인한다. 기존 MAIN 브리지의 답변 쓰기 경로를 새 비교기에 복제하지 않는다.

구현에서는 순수 분석기와 비교기를 `gpt-protocol.js` 안에 두어 기존 주입 순서를 유지했다. 별도 자연어 모델은 없으며 명시적 신호를 분류하지 못한 문구는 원문으로 남긴다. 기존 긴 지침의 제한된 예시/공백 호환 경로를 유지한다. `※` 뒤 알려진 작성 안내의 생략은 식별자·본 질문·유일성이 확인되는 경우만 허용한다. 혼합 분량 그룹의 내부 경계가 불명확하면 전체를 보존한다.

확인 대응의 보관·삭제까지 이번 변경에 포함했다. 최대 256개/30일이며, 문항 구성 SHA-256과 분석기 버전까지 범위를 검사한다. 준비 뒤 전체 문항 구성의 원문 지문도 재검증한다. 구현 결과와 기존 버전 비교는 [검증 기록](../tests/gpt/README.md)의 2026-09-14 공통 분석기 절을 따른다.
